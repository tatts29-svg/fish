## Findings to resolve before release

1. **P1 — The pump-out gate has exceptions to Andrew's absolute rule.** `demob816_src.js:90–97` allows a normal delivery-light change before 19 Oct, and allows it after that date whenever the previous light is not `on site`. A missing/incorrect existing light is not evidence that a toilet or tank has been emptied. The forced Demob action closes those two exceptions, but the existing drawer light uses the unforced gate (`patch_v816.py:66–71`). Also, `emptied:true` with no person or timestamp passes both paths. Offline fixtures reproduce all three. Distinguish an incoming delivery from an outgoing collection explicitly, and apply a valid, attributable pump-out prerequisite to every outgoing loading/transport path. Do not make date or an absent green light a collection exception.

2. **P1 — A pump-out tick is not tied to the current use/collection cycle.** `demob816_src.js:67–70,95` accepts any historical `emptied:true`; the unchanged `setLight` does not invalidate it when the reference comes back on site. Offline reproduction records a new `on site` state while retaining an earlier pump-out tick: the next forced collection is allowed. The lookup also prefers any local boolean to a newer committed untick, without comparing `emptied_at`. Bind the clearance to the relevant units/current use cycle, preserve the newer revocation, and show whose current clearance permits loading. Test reuse, revised unit quantities and a newer false value, rather than only the first false-to-true tick.

3. **P1 — Import merging deletes the new pump-out record and audit history.** The patch only extends `deliveryEmpty` (`patch_v816.py:72–74`); v8.13 `mergeRecords` rebuilds delivery documents through a fixed list of fields and histories (baseline lines 35106–35140). It has no `emptied` group or `emptied_history` union. The exact function returns an empty delivery map when merging a reference containing only the new tick, name, timestamp and history with an empty record. With other delivery fields present, those fields survive but pump-out evidence still disappears. Plain export carries the delivery document; the loss is on merge. Add the new value/stamps/history to the existing deterministic merge, validation and audit paths, and prove export/import preservation, later untick precedence and idempotent merge. Do not claim the new operational clearance is durable from `deliveryEmpty` alone.

4. **P1 — A split portable-toilet reference receives conflicting dates.** `pack816` correctly splits 25 units into 24 and 1, but `demob816_src.js:159–161` assigns each load's date to the same shared reference object. A single proposed outside reference with 25 FWF units yields 24 units on Mon 26 Oct and 1 on Tue 27 Oct, while both rows advertise the reference date as Tue 27 Oct. The reference is absent from Monday's pick-up list and therefore its confirmation set; confirming Tuesday saves one date for all 25 units and repacks the plan. Preserve the 24-unit cap while keeping split load quantities, dates, pump-out tasks and confirmation aligned; alternatively keep all parts of a reference on one day until partial collection is represented. The supplied unit-total test does not detect the inconsistent date.

5. **P1 — Toilet-before-tank ordering is local to one stop, not across runs.** `demob816_src.js:226–230` sorts non-tank parts before tank parts, but `trucks816:238–258` builds normal and portable-toilet runs independently. In a supported mixed reference with one FWF and one waste tank on the same day, the tank run is listed first and loads at 07:00–07:30, concurrently with the toilet run at 07:00–07:15. This is a synthetic mixed-reference case, not a claim that a current live reference has that exact composition. The renderer explicitly supports mixed references, and the current test only checks part order inside each stop. Preserve the real supporting-toilet relationship and order its removal before the tank across separate loads/references; if the relationship is unknown, show it as unresolved rather than issue a sequenced tank run. Test separate-run and separate-reference pairs.

6. **P2 — Unknown unit quantities become definite one-unit collection instructions.** `demob816_src.js:62–64` substitutes `1` and sets `assumed:true`, but no downstream load, row, print or email renders that flag. A reference with both quantities unknown becomes a one-unit load and a definite `1 ×` run-sheet line. This can understate the 24-unit capacity, pump-out checks and duration. Keep unknown quantities explicit and out of firm capacity/clearance claims until resolved. The fixture reproduces `units:1, assumed:true`; the supplied tests verify totals against the same inferred source and cannot detect this issue.

7. **P2 — The narrow Timeline correction still drops some typed removal dates.** Independently reproduced using the exact baseline `effectiveDates`/`programmeDaysBefore801` and the patch hunk at `patch_v816.py:85`. An added reference with `_added:true`, `first_date:'2026-10-20', last_date:'2026-10-20'`, no events and a typed `out_date:'2026-11-04'` has `eff.out_plan:'2026-10-20'`. Existing programme construction creates only its delivery, and the new `!eff.out_plan` condition prevents the typed removal from being added. The output contains no 4 Nov removal despite the saved date. Base the correction on the absence of an actual removal event, while preserving one removal per reference/day. Ordinary no-plan references work. Add the same-day added-reference case to the tests.

8. **P2 — Cancelled references hide an existing recorded Out date in the drawer.** `drawer816_src.js:119,124–134` renders the Out summary solely from `demobOf816`; the model deliberately excludes cancelled/removed references at `demob816_src.js:136`. A cancelled reference with a typed out date therefore shows `—` / `no date - position to confirm`, despite `effectiveDates(a).out` retaining its date. Keep the active Demob exclusion, but fall back to the authoritative effective date in the drawer. This is source-established; no browser assertion is claimed.

## Evidence and scope

`evidence/demob_cpu_audit.js` evaluates the frozen Demob functions with small isolated fixtures plus the exact baseline `mergeRecords` and `setLight`. Its JSON is a set of observed failures, not a passing release suite. Run with:

```sh
node evidence/demob_cpu_audit.js /path/to/frozen/demob816_src.js /path/to/v8.13/GC500_Delivery_Control_hosted.html
```

The draft has useful safeguards: date source labels remain separate; proposing dates only mutates the computed model; date/tick/collection setters check edit capability; the weekday window is generated with explicit UTC midday; maximum portable load size is 24 for valid positive quantities; oversized runs explicitly say to check permits; times are labelled as a planning sketch. No unsolicited operational writes were found in the rendering path. The draft's date setter remains the existing page function, and no automatic date confirmation was found.

The 5 min per portable and 4 pieces per normal truck are explicitly labelled assumptions, not verified travel/capacity facts. This review does not establish their operational suitability. Existing authoritative dates are preserved even when they fall outside the proposed outside-first sequence; contradictory fixed dates should stay visible rather than silently move. Weekends inside the overall range currently have no day board, so future typed weekend dates also need a deliberate visible treatment. No timezone regression was found in the narrow Timeline hunk; full browser, Brisbane-boundary, record round-trip, recurrence, fresh-base build, standing suites, all-tab navigation and visual/print checks remain for the corrected release candidate.

The supplied `v816_tests.js` covers one green, first-time pump-out path, current-data part order, unit totals and an ordinary P42 typed date. It does not cover the failure cases above. This review is actionable draft feedback, not a READY handover.
