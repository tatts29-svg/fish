# v12.42.3: Demob saves quicker — DRAFT

Author: Andrew Fisher · 27 Oct 2026 · a point release on live v12.42.2 (truck loads from what is Ready, `c83f1a27…`).
**DRAFT: built and tested locally (desktop and 4x phone), measured before and after. Not uploaded.**

Andrew, 27 Oct 2026, on site at the Coates GC500 demob: "Delay when saving in demob can we make this quicker".

## What was slow (measured on live v12.42.2)

Every save on the Demob tab was one blocking task. The card and the flash only changed when that task ended.

| Press | Desktop | Phone (CPU 4x) |
|---|---|---|
| Not ready | 9.1 s | 28.8 s |
| Ready | 7.3 s | 29.3 s |
| Book pick-up (one unit), Save | 5.6 s | 20.8 s |
| Book this load, Save | 4.5 s | 17.5 s |
| Picked up, first recording Emptied | 5.2 s | 23.3 s |

Times are medians from the press to the change on screen (401 cards, about 34,400 elements on the tab). Where the time went:

1. **Keep-your-place, 74% of a phone save.** This is the step `bump()` runs before every save, Persistence1010's `capture()`. It read the scroll position of every element on the tab (about 34,000). Each card is drawn with `content-visibility:auto`, so each read inside an off-screen card made the browser lay that card out first. That was about 440 layouts per save, to find the one strip that had scrolled: 16.4 s on the phone and 4.2 s on a desktop, before anything was stored.
2. **Drawing all 401 cards again** after every save: about 4 s on the phone, plus 4 to 6 s of layout and paint afterwards.
3. **The cards' model built outside the page's asset hold.** The asset list was rebuilt for every lookup: 7.6 s on the phone against 0.55 s inside the hold. The lights, the booking sheet's clash check and its Save all hit this whenever the model was over 4 s old. The save's own footer redraw rebuilt the day's plan outside the hold too (1.1 s on the phone).

## What changed

### 1. Keep-your-place reads only what has scrolled (shared save path: to be reviewed by whoever owns it)

Persistence1010 `capture()` (`patch_v12423.py`, three exact replacements):

- One passive, capture-phase `scroll` listener on `document` notes each element that scrolls, whether a finger or the page scrolled it. It lets go of elements no longer on the page.
- `capture()` reads `scrollTop`/`scrollLeft` only for the tab itself and the noted elements still inside it. It takes them in page order and stores them under the same keys in the same format. So the list it keeps is the same list the old read-everything loop found.
- `restore()` puts back exactly what it did before. It now also notes each element it scrolls back. That covers a second save in the same moment, before the browser's own scroll event arrives.
- `bump()`, `save()`, `persist()`, `bump.kept` and the sync are not touched.

The test checks the new list against reading every element, with the day strip, a day card's list and the group chips scrolled. It gets the same elements, keys and positions. It then checks that a save that draws the whole tab again puts each of them back, and that two saves in one moment do too. On its own, `capture()` drops from 4.2 s to about 7 ms on a desktop (phone: see below).

### 2. The Demob module (singles1238, generated by `make_src_from_v12422.py`)

- **The model is built inside the page's asset hold.** `model()` first checks, without building anything, whether the model it already has still stands. That means nothing saved since, under 4 s old, and the day's plan is the very one it was built from (the same rule as before). If not, it builds the model again inside `holdAssets`, so the asset list is built once.
- **The taps that read the model run in the hold:** the lights, Book pick-up, Book this load, and the booking sheet's day, time and Save.
- **A unit's Ready tick and a booking are quick saves.** The save is still the page's own `bump()`, run inside the hold:
  - the change is stored in this browser first, then queued for the shared record;
  - its answer is read as before: `bump.kept === false` still says "Not saved · keep this page open" and never "recorded".

  This covers Ready, Not ready, one unit's booking, "Book all" at a reference, Clear and Book this load. During that save the Demob redraw does not draw all 401 cards again. It puts right, in place:
  - the cards of the references the save wrote;
  - the counts;
  - the section and group heads;
  - the truck loads and the booked pick-ups;
  - the day cards and today's "Ready for collection" figure.

  It works all of that out from the model before it changes anything on screen. A card changes node by node, so the button just pressed keeps its place and focus and the card's two pictures stay as they are.
- **What is redone after a quick save, and why that is enough.** A booking reruns the day cards' lists and figures and the headings, as after any drawing. A Ready tick changes none of those, because they count bookings and departures. So after a Ready tick only today's "Ready for collection" figure is put right, and the filter is applied again if one is on.
- **The model as drawn is brought up to date for a quick save.** Only that save's references are read again, for their cards' lights and bookings. This is used only when nothing else was saved since, and the model still stands by `model()`'s own rule or was found good earlier in the same tap. The tap and its save run as one piece of script, so nothing from outside can change the record in between. Otherwise the model is built again.
- **When a quick save is not used.** The whole tab is drawn exactly as before if any of these holds:
  - the tab is not showing the cards as last drawn (another view, day, branch or link);
  - the cards on screen are not the same cards in the same places;
  - any card the save did not write has a light or booking that differs from what was drawn;
  - a booking adds a card to the day's list on screen, or takes one off it.

  Every other save also draws the whole tab as before: Emptied, Picked up and the departure form, a reference's own Ready tick, and remote changes arriving on the sync.

## What did not change

- What is stored and what is sent: the same documents, fields, stamps and history lines.
- `bump()`, `save()`, `persist()`, `syncPush`, the live-sync merge (`keepUnits`, `um1238`), mergeRecords and refused saves.
- No change is shown before `bump()` has stored it. A save this browser could not keep shows what the old full redraw showed (the change on the card) and says "Not saved · keep this page open".
- How the cards, trucks, booked pick-ups and day cards read. The test compares each quick save with the whole tab drawn again straight after; they read the same.

## Still slow, and why it was left

What is left in a quick save on the phone is mostly the page's shared save and draw path, which this release does not change. Desktop figures are from the profile of a Ready press; on the 4x phone each is about four to five times as long.

- **`save()`, about 0.23 s on a desktop and 1.0 s on the phone.** That covers `renderTabs`, the `syncFooter` wrappers (staff988's `mountDemob` builds the day's plan again, now inside the hold) and `syncStage`/`syncPush`. `persist()` itself is only 0.02 s (desktop) and 0.1 s (phone).
- **The page's `render()` wrappers above the Demob tab, about 0.2 s on a desktop and 0.8 s on the phone.** These are other modules' wrappers (Drops911, SelectionSave1012, DayRefresh1103, v8.92), plus `renderPass`'s own extras (hzTodayPod, financeOperational857, applyCapability and the fold passes).
- **After the change is on screen, v12.36's `after()` runs again on the next frame.** Its watcher sees today's day card figure change. Its `titles()` asks `Singles1238.count()`, which builds the model again whenever the page has emptied its drawing memo in between: 0.25 s on a desktop and 1 s or more on the phone. This lengthens the time until the page is idle, not the time until the change shows.
- **Saves that still draw the whole tab** only get the keep-your-place and hold savings. These are Emptied (Picked up that first records Emptied), the departure form, a reference's own Ready tick (the group cards) and remote changes arriving on the sync. Picked up with Emptied: desktop 5.2 s to 1.9 s, phone 23.3 s to 8.6 s.
- **The page's background on the phone:** the sync poll every 4 s (`pull()` with the `syncFooter` wrappers and `applyCapability`), about 0.85 s of long tasks every 4 s. It can hold a tap back by up to about 0.4 s before the save starts.
- **A tap more than 4 s after the cards were last worked out builds the cards' model again before saving.** That is `model()`'s own rule, kept as it was, and now done inside the hold: about 0.15 s on a desktop and 0.7 s on the phone (it was 1.6 s and 7.6 s outside the hold). Trusting the model for longer would take that off too. It would change how long the module trusts a model without the page drawing again, so it is left as a question rather than done here.
- **Positions are looked up again every 30 s** (`locOf`, so a moved pin moves the pictures). The first truck plan after that relocates every Ready card.

Taking the next second off the phone needs changes in the shared path: `renderTabs`, the `syncFooter` wrappers, and the render wrappers that run whatever tab is showing. That needs agreeing with the shared code's owner on the board first. Those are the next things to measure.
