# Departure order and source prerequisites

Author: Andrew Fisher

The booking release already separates the DD departure rank from the loading clock. These controls record the checks for each actual booked truck and the operator/time of departure. They use the existing dispatch cards, drawer and checkbox components. They do not change delivery lights, installation ticks, fencing quantities, dockets or commercial records.

`patch_dispatch803.py` follows `patch_v803.py`. Its source is `dispatch803_src.js` and `sequence803_src.js`. No new shared collection or local-only release record is introduced. No live records have been created by this implementation task.

The existing `loads` map stores `dispatch803` under the native date/truck key, preserving pairing, drop card and other record fields. Cargo, applicable full pre-transit checklist and driver instructions require explicit named, timestamped confirmations. The existing direction check applies to every reference on the truck. All lower DD ranks need acknowledged named/timestamped departure records before the current truck can depart; equal ranks may depart in either order. Both seventh-ranked tanks precede both eighth-ranked blocks. The shared fourth truck remains one record. GN18 is held for its missing rank and unresolved asset allocation conflict.

A live shared connection and a heartbeat no older than 15 seconds are required. Pending checks and departures remain pending until the existing shared-record acknowledgement agrees with the current value. A new booking, pairing or direction changes the confirmation signature. An existing departure remains visible if its booking subsequently changes; it is not silently rewritten. An invalid historical departure is displayed for review and cannot satisfy a predecessor requirement. A failed local save restores the edited load/answer and its stamp; the existing storage failure state continues to prevent release.

The pre-transit source was retrieved and read: `Site_Accommodation_Pre-Transit_Checklist_Work_Instruction.pdf`, TRAN-WI-R1.2, version 2.0, 19 Nov 2019, ten pages, SHA-256 `31bdabf6ab090ffbdc8c166cb4b5ed60639791bd1102cd6639a5f9af2e23e4b3`. The drawer links the full existing instruction. The brief reminders cover the applicable structure, services, fittings, liquid storage, lifting/restraint and roof checks without presenting the reminders as the full checklist. JSEA before unloading and Take 5 remain separate from departure and installation completion.

Fencing prerequisites use the supported `answers` value collection through `setQAnswer`. Keys include a source-hash prefix plus task and requirement IDs; the value retains the full PDF hash, revision, exact instruction, confirmation/revocation, operator and time. The complete value must survive the setter's 600-character limit without alteration. Only valid owned answers attached to a visible fencing task are excluded from orphan Questions; ordinary unknown answers remain visible. Earlier-source confirmations remain visible on the task but do not satisfy a current requirement. Conditional instructions are recorded as reviewed with the crew, not as proof that their future conditional work has been completed.

Implementation checks use the read-only harness and isolated browser records. Shared acknowledgements are exercised through the page's native `syncSettled` function; the live service receives no test writes. Independent persistence and actual-control review are in progress.
