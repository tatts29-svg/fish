# Speed diagnosis: idle/sync findings and the overall plan (18 Oct 2026)

Author: Andrew Fisher · the last two parts of the diagnosis, saved by Claude for Codex (v10.66 owner). Verbatim from the diagnosis run; the earlier parts are in speed_findings.md.

## idle/sync findings

### Every new record version makes the whole visible tab redraw, even when nothing synced has changed (the 'loads' quantity-scope cache always compares as different)
- area: idle
- confidence: high
- cost: Measured by re-delivering the same record (SYNC.backend.pull(true) is the same code path a version bump takes), 30 s window, medians of 3. Phone 390x844, CPU x4: Today 12.97 s of main-thread work, with one task of 9.0 s (8.3-9.9 s across runs). Build 30.4 s of work in the 30 s window: longest task 3.2 s, 12.4 s of long tasks (render 2.2 s, the Build table refilling 23 s, Persistence capture 0.7 s). Desktop: Today 6.5 s of work with a 2.0 s task; Build 4.4 s with a 0.7 s task. This happens on every version bump from any writer, including writes to documents that change nothing on this page.
- root_cause: Inline script #3 (main app), syncFold() at page line 54124, compares `JSON.stringify(next) === JSON.stringify(c.get())`. v10.17 scope_sync1017.js (inline script 117, id quantity-scope-sync1017-script, page line 87780) overrides `SYNC_COLLS.loads.set=function(v){return loadsSet0({...without(v),...scopes(S)});}`, so S.loads always holds the private scope cache. fromDocs('loads') from the service never holds it, so 'loads' always compares unequal. Each delivery then runs c.set (same content), sharedCache975(), persist() (localStorage write of the ~0.9 MB record) and syncRedraw(). That goes Persistence1010 background, then redraw, then render() of the current tab. Confirmed by wrapping syncFold: on 3 of 3 re-deliveries only 'loads' returned true, and JSON.stringify(S.loads) was identical before and after set ('same-json-after-set').
- fix: In syncFold (inline #3) replace
  if (JSON.stringify(next) === JSON.stringify(c.get()) && (name !== 'qtys' || ScopeSync1017.same(next,S))) return false;
with
  const cur1061 = JSON.stringify(c.get());
  if ((JSON.stringify(next) === cur1061 || (c.wouldBe && JSON.stringify(c.wouldBe(next)) === cur1061)) && (name !== 'qtys' || ScopeSync1017.same(next,S))) return false;
In scope_sync1017 (inline #117), after the loads.set override, add
  SYNC_COLLS.loads.wouldBe=function(v){return {...without(v),...scopes(S)};};
The save status lines read SYNC.last, which a delivery refreshes. They used to be redrawn by the forced redraw, so in pull() change
  deliverAll();\nif (SYNC.status !== 'live') { SYNC.status = 'live'; syncFooter(); docsRedraw(); }
to
  ... docsRedraw(); } else syncFooter();
All three are in patch_v1061_idle.py, fix 'fold'.
- gain: Phone CPU x4, medians of 3 back-to-back: Today re-delivery 12.97 s to 2.03 s of work, longest task 9.0 s to 0.24 s. Build 30.4 s to 1.42 s, longest task 3.2 s to 0.16 s, long-task total 12.4 s to 0.16 s. Desktop: Today longest task 2.0 s to 0-65 ms (6.5 s to 3.9 s of work, spread out); Build 4.4 s to 0.42 s.
- parity: In both pages JSON.stringify(S) was identical before and after pull(true), and identical between base and prototype (918,775 chars, same hash, live version 9704). syncRedraw calls went from 1 to 0. innerText and textContent of all 17 tab panes were identical on desktop and phone (one desktop capture differed only by a Build-card 'Loading…' placeholder that one more card had already resolved; both show the same 80.06% value). Simulated edit link (aborted writes): Save-bar counts and states, the typed 'Unsaved change', restore after render() and drawer bars were identical. Both toolchain sweeps: 0 errors, 0 console errors.
- risk: Low. A delivery that really changes a synced collection still redraws exactly as before. The only lost path is the forced redraw after a delivery that changed nothing. Status text that reads SYNC.last and is not wrapped by syncFooter would wait for the next poll (4 s) or the next real change.

### Header clock and observer ping-pong: the clock replaces elements every second, which makes the v10.12 Save-bar observer rescan the whole page
- area: flicker
- confidence: high
- cost: Phone CPU x4, idle on Today: selection-save mount() ran 75 times a minute, 2.2 s/min, up to 75 ms each. Today had 36 long tasks/min totalling 2.4 s and 2.57 s/min of script. Build: mount 2.1 s/min, 16 long tasks/min. Desktop: 0.52 s/min on each tab. Five other document-wide observers also woke every second (hostedMedia wire, icons989 enroll, cleanText, scene896, motion install), about 0.1 s/min together on the phone.
- root_cause: Inline #3 tpodPaint() (page line 50411) runs once a second from tpodTick and sets num.innerHTML (#tpodNum: span.d, span.sep x2, span.sec) and sub.innerHTML (#tpodSub, a <b>). It also replaces the text nodes of #tpodDate, #tpodLab, #tpodSrc and #tpodNote with the same text, and hzCountdownTick sets #hzcdT.textContent. recStrip() (line 54318) rewrites #recstrip.innerHTML on every poll. v10.12 selection_save1012.js (inline #105, page line 86856) has `new MutationObserver(...)` on document.body {subtree, childList} that calls schedule() for any added or removed element. schedule() then runs rAF mount(), which does document.querySelectorAll(selector) with about 40 attribute selectors over 23-35k nodes, then identity/entry/restore/draw for every field.
- fix: (a) Fix 'clock': add text1061, shape1061, fill1061, html1061 and attr1061 before tpodPaint. html1061 parses the new markup into a template and, when the element and attribute shape matches, updates only the changed text nodes; otherwise it sets innerHTML as before. In tpodPaint use html1061(num, ...), attr1061(num,'aria-label',...), text1061 for dt, lab and src, html1061(sub, ...) and text1061(note, ...). In hzCountdownTick use text1061(el, h:m:s).
(b) Fix 'observe': in inline #105 replace the observer with
  new MutationObserver(records=>{if(records.some(r=>[...r.addedNodes].some(n=>n.nodeType===1&&!n.matches?.('.selection1012-controls,.selection1012-controls *')&&(n.matches(selector)||n.querySelector(selector)))))schedule();}).observe(document.body,{subtree:true,childList:true});
mount() only acts on fields that are in the document, so only an added node that is or contains a field can give it work.
(c) Fix 'fmt': tpodParts reuses one Intl.DateTimeFormat (tpodParts.fmt) instead of building one every second.
- gain: Phone CPU x4, medians of 3: mount time went from 2198 to 41 ms/min on Today and from 2107 to 0 on Build. Today long tasks went from 36 to 3-7 per minute (2408 ms to 178-395 ms), script from 2.57 to 0.29 s/min, and the clock's own cost from 226 to 140 ms/min. Desktop: script on Today 0.62 to 0.07 s/min, mount 519 to 11 ms/min.
- parity: #tpod, #hzcd, #hzshift, #tpodSec and #hzcluster outerHTML were identical between base and prototype after painting 9 fixed instants in clock, countdown and clock modes (135 snapshots, desktop and phone, including the in-place updates). Save bars matched in view and simulated edit: costs 59, pricing 130, drawer 139, with the same state and status strings, the typed dirty state surviving render() and the restored value equal. All pane text was identical.
- risk: Low. A Save bar removed while its field stays in the document would no longer be recreated by an unrelated mutation, but the original filter already ignored removed bars. Status lines no longer get an incidental refresh from unrelated DOM churn. They are still refreshed on input, change, save and every syncFooter.

### Every 4 s poll with an unchanged version runs 9 chained syncFooter wrappers, including a whole-page Save-bar rescan
- area: idle
- confidence: high
- cost: Phone CPU x4: the syncFooter chain cost 1.0 s/min on Today (about 85 ms per poll, max 154 ms; 15 polls/min) and 0.72 s/min on Build. Inside it: the selection-save refresh 0.42 s/min, the staff988 roster rebuild 0.28-0.40 s/min, four document-wide querySelectorAll feedback functions (035 feedbackDraw1006, 096 drawStatus, 101 and 104 feedback) about 0.14 s/min, and core syncFooter (recordBytes reads the whole record from localStorage) about 0.06-0.09 s/min. The unchanged-version path does not re-render panes.
- root_cause: In inline #3 restBackend pull() (page line 54438), `if (!force && v.version === version) { syncFooter(); ... return; }` runs every 4 s. syncFooter has wrappers from inline 035, 074, 080, 084, 096, 101, 104 and 105 plus the wip lamp. 105's `function refresh(){for(const el of document.querySelectorAll(selector)){...draw(el,f)}}` (line 86795) rescans the page, although draw() returns early for any field without a connected bar.
- fix: Fix 'refresh' in inline #105:
  const live1061=new Set();
  function refresh(){for(const el of [...live1061]){if(!el.isConnected||!mounted.get(el)?.isConnected){live1061.delete(el);continue;}const f=family(el);if(f)draw(el,f);}}
and in mount() change `}draw(el,f);` to `}live1061.add(el);draw(el,f);`. This draws exactly the fields that have a connected bar (family() is still checked), without the whole-page query. Not prototyped: memoising staff988 html(day) per poll, scoping the four feedback queries to the open drawer or pane, and caching recordBytes.
- gain: Phone CPU x4, medians of 3: syncFooter chain 1016 to 573 ms/min on Today and 723 to 347 ms/min on Build. Desktop 246 to 151 ms/min on Today and 166 to 86 on Build.
- parity: The same Save-bar parity as the clock finding (counts, shown, state and status strings after typing, syncFooter, render and drawer open), plus all pane text identical.
- risk: Very low. The Set holds removed fields only until the next refresh prunes them, at most 4 s later.

### The Build tab's completion-ring glow animates 24-148 rings that sit inside folded sections, forcing a main-thread frame every vsync
- area: idle
- confidence: high
- cost: Phone CPU x4, idle on Build after the table has filled: 584 frames per 10 s, 1.02 s of BeginMainFrame per 10 s (about 10% of the main thread) and continuous GPU commits. Pausing just these animations dropped it to 23 frames. In the 60 s A/B this is most of Build's remaining native time: 3.07 s/min of (program).
- root_cause: v10.08 complete1008.css (inline style complete1008-style, page line 11385) sets `.complete1008-badge .complete1008-ring,.complete1008-done .complete1008-ring{animation:complete1008-glow 3.4s ease-in-out infinite}`. That is an opacity animation on an SVG <path>, which Chrome cannot composite. Every running ring is inside a closed <details class="fold96 eqrefs"> on the Build tab, so none of them can be seen, but Chrome still ticks them. They are not in a content-visibility card (no contentvisibilityautostatechange fires), and animationstart never fires for them.
- fix: Fix 'glow': append after `@keyframes complete1008-glow{...}`:
  details:not([open]) > :not(summary) .complete1008-ring{animation-play-state:paused}
This is CSS only. It has higher specificity than the original rule, the page's motion-off `animation:none!important` still wins, and rings inside a summary are not matched.
- gain: Phone CPU x4: 584 to 21 frames per 10 s, BeginMainFrame 1020 to 127 ms. 60 s Build idle, medians of 3: busy 6.5% to 3.6% on top of the other fixes; (program) 3073 to 935 ms/min. Desktop Build idle busy 3.5% to 0.8% with all fixes.
- parity: Before opening the folds, every ring in a folded section is paused in the prototype (148/148) and running in the base. After every fold is opened, all 148 rings are running in both pages. Pane text was identical.
- risk: Low. A ring's pulse resumes from where it paused, so the phase can differ from a ring that was never folded. A print stylesheet that shows closed-details content (#where885 .p907-programme in print) prints the ring at its paused opacity, which is within the 0.55-1 range the base already prints at random.

### The Build table fill rebuilds the whole asset list thousands of times on a phone and takes about 4.6 min to finish
- area: build
- confidence: high
- cost: Phone CPU x4 (go('plant') until the table is complete), 3 runs: base 193, 276 and 297 s (median 276 s), with 6,097-9,808 buildAllAssets() calls (median 8,930) costing 165-260 s of main-thread time, to place 9 batches of rows. Desktop: 2.3 s and 10 builds. The page is busy for minutes after opening Build. It also slows idle measurement: the A/B idle windows were started only after this finished.
- root_cause: Inline #3 plantPump() (page line 15208), step: `const t0 = performance.now(); holdAssets(() => { while (qi < q.length && performance.now() - t0 < 10) if (plantFill(pane, q[qi], qi, 6)) qi++; });`. t0 is taken before holdAssets(), and holdAssets() rebuilds the whole asset list first (buildAllAssets, wrapped by lighting894 inline #017; 27-40 ms per call on the phone). When the rebuild takes 10 ms or more, the loop fills nothing, the step reschedules (rAF then setTimeout 0) and rebuilds again. It only progresses when a rebuild happens to finish in under 10 ms.
- fix: Fix 'pump': replace that line with
  holdAssets(() => { const t1 = performance.now(); while (qi < q.length && performance.now() - t1 < 10) if (plantFill(pane, q[qi], qi, 6)) qi++; });
It is the same fill in the same order; only the 10 ms budget now starts after the one rebuild per step.
- gain: Phone CPU x4, 3 runs each: median 276 s to 12.0 s (11.4, 12.3, 12.0 s), buildAllAssets calls from a median of 8,930 to 10. Desktop: no real change (2.30 vs 2.48 s, within run-to-run spread).
- parity: In all 12 runs (phone and desktop, base and prototype) the Build pane had 96 rows, and its innerText and textContent hashes were identical (textContent 26,163 chars). Full-tab parity (which waits for the fill) was identical.
- risk: Low. Each step is now one rebuild plus about 10 ms of rows, so steps are slightly longer on desktop. This overlaps the Build-tab investigation, so coordinate before both land.

### Today's 'Where we are' race-light sweep uses about half of a phone's main thread while it is on screen (not prototyped)
- area: flicker
- confidence: medium
- cost: Phone CPU x4, Today scrolled to the Where-we-are lights: 391 frames per 10 s, 4.63 s of BeginMainFrame per 10 s (46% of the main thread), with Paint about 1 s, plus Layerize and PrePaint. Pausing only tw846-visible-sweep dropped this to 0.42 s per 10 s. Desktop Today: 0.88 to 0.10 s per 10 s. On desktop it is most of Today's remaining idle cost: busy 11.8%, of which (program) is 5.4 s/min, unchanged by the other fixes. When the card is off screen the page already pauses it (w885-running).
- root_cause: The CSS `#where885 .w885-lights .race-sweep-window {animation:tw846-visible-sweep 2.4s linear infinite...}` (page line 9163), and the equivalent work-board840 rule, animate the transform of a <rect> inside an SVG <clipPath>. The clipPath is injected by inline #013 where885-script and by timeline841 lamp HTML. A clip-path child cannot be composited, so every vsync re-runs style, layerize and paint of the lamps, including the 62% hold phase of each cycle when the window sits off the lamp.
- fix: Not prototyped, because it changes how the component is drawn and needs a mock-up and Andrew's yes. Proposal: draw the sweep with compositor-only transforms on HTML wrappers instead of the clipPath rect. An outer 11 px window translates across while an inner copy of the dots counter-translates, giving the same look. A lesser option is to promote each lamp <svg> to its own layer, which only partly reduces the paint.
- gain: Not measured on a prototype. The upper bound measured by pausing the 4 running sweeps is phone 4.63 s to 0.42 s per 10 s while the card is on screen, and desktop 0.88 s to 0.10 s.
- parity: n/a (not built)
- risk: Visual: the sweep must look the same; screenshot comparison needed.

## notes

I built a prototype on a copy of live v10.60.1 with seven fixes. On the phone (CPU x4) it roughly halves idle work on Today, cuts it by about two-thirds on Build, removes the 9-30 s freezes when another device saves, and takes the Build table fill from about 4.6 min to 12 s. Nothing in the repo or the live record was touched.

Phone idle, 60 s windows, medians of 3 back-to-back runs, base -> prototype (proto2_glow):
- Today: busy 9.6% -> 5.3%; long tasks 36 (2.4 s) -> 7 (0.4 s); script 2.57 s -> 0.29 s.
- Build: busy 11.4% -> 3.6%; long tasks 16 (0.9 s) -> 0.
- Same record re-delivered (a version bump with nothing changed), 30 s window: Today 12.97 s of work with a 9.0 s freeze -> 2.03 s, longest task 0.24 s. Build 30.4 s with a 3.2 s freeze -> 1.42 s.
- Build table fill (proto3, which adds the pump fix): 276 s -> 12.0 s.
- Desktop: Build busy 3.5% -> 0.8%; Today script 0.62 s -> 0.07 s/min. Desktop Today stays at 11.8% because of the race-light sweep (finding 6).

What runs while the page sits idle (phone CPU x4, per minute):
- Timers:
  - Poll: setInterval 4 s (inline #3 page line 54488, only while visible). 15 GETs to /api/version per minute. /api/state (about 0.9 MB) is fetched only when the version changes.
  - Clock: tpodTick chain about once a second (stops when hidden). 0.23 s/min base, 0.14 s/min prototype.
  - scheduleHealth: 2 s timer on Today (returns when hidden), 45 ms/min.
  - Photo outbox: 60 s.
  - Not running on Today or Build: 138 shapes pull (10 s), 028 map health (1 s), show-mode clocks and watchdog, ms1026 retry. The first two are gated on document.hidden.
- requestAnimationFrame: the only loop running on Today or Build was the selection-save mount (2.2 s/min).
- MutationObservers: document-wide ones in #3 (hostedMedia, cleanText, two motion/health installs), 020 scene896, 012 demob826, 073 icons989 and 105 selection-save.
- Hidden tab: the existing gating is already correct, so no 'pause when hidden' change is needed.
- After visiting the Map tab and returning (desktop, GL on), no extra loops were left running.
- Ping-pong found: the clock feeds the 105 observer (finding 2) and recStrip feeds the same observer on every poll. No self-sustaining render loop.
- Clock repaint: about 1 layout per second (layoutN 90/min), cheap; its real cost was the observer fallout.

Remaining after the fixes, not prototyped:
- staff988 roster rebuilt on every poll: 0.28 s/min.
- Four document-wide feedback queries: 0.14 s/min.
- recordBytes reading the whole record from localStorage every poll.
- A version bump with a real change still renders the whole visible tab: Today about 9 s on the phone, Build about 25 s.

Method and caveats:
- Settle rule (same for both pages): at least 150 s after load on the phone (40 s desktop), then 10 s with no task over 250 ms, and the Build fill finished. The base Today never had 6 s without a task over 50 ms, so an early-settle rule was biased and I re-ran the whole A/B.
- Busy % is CDP Performance TaskDuration over wall time. Attribution is from CPU profiles sampled every 0.5 ms.
- The Build-switch wall time (go('plant') until filled, 3 runs each) was too noisy to call a gain. Base filled at 101 and 74 s and once not at all in 240 s; the prototype (with the observer fix but not the pump fix) filled at 72, 145 and 235 s. Desktop profiles show selection-save cost on the switch dropped from about 50 ms to 7 ms, with no regression.
- The harness parks a mouse pointer, which adds hit-testing to traces; this inflates both pages equally.

Parity:
- 17 tab panes, innerText and textContent, desktop and phone.
- Clock markup at 27 fixed instants in clock and countdown modes.
- Save bars in view mode and a simulated edit mode (aborted writes): costs 59, pricing 130, drawer 139, with the same state strings.
- S identical after re-delivery (918,775 chars, live version 9704).
- Ring states in folded and opened sections.
- Build pane text hashes identical in all 12 fill runs.
- check_page.py PASS; both toolchain sweeps (desktop and phone) 0 errors and 0 console errors.

Coordination: the pump fix (finding 5) and the race-light sweep (finding 6) overlap the Build-tab and flicker investigations. Finding 6 changes how a component is drawn, so it needs a mock-up and Andrew's yes before anyone builds it.
